# Pipeline state retention on the self-hosted runner — design

**Status:** approved 2026-10-27 · **Scope:** GitHub Actions runs of the OP Teleconsultation pipeline

## Goal

The Control Code Tracker keeps its data across GitHub Actions pipeline runs, so every
control code generated by CI stays traceable from S0 to S10: where it is, where it is
stuck, and what happened to it.

Only GitHub Actions writes this tracker. Teammates read it (run summary, downloaded
artifact); local runs keep their own, separate trackers.

## Context

- The tracker is `test-data/control-code-tracker.xlsx` (gitignored). `actions/checkout`
  cleans git-ignored files on the self-hosted runner, so without help every run starts
  with an empty tracker.
- The tracker cannot be retained alone. Later stages read the intake files under
  `test-data/<CHANNEL>/<date>/`, and `scripts/.intake-sequence-state.json` holds the
  filename counter. Losing the counter restarts today's codes at `…00001T`, so S1 would
  upload control codes that were already uploaded to the real Azure Blob storage.
- There is one runner: AVD-BASCL06-0, labels `self-hosted, windows, op-pipeline`.
- The first version of this already exists inline in
  `.github/workflows/op-intake-pipeline.yml` (restore/save steps copying to
  `%USERPROFILE%\claims-qa-state\op-pipeline`). This design replaces that.

## Decisions

| Decision | Choice | Why not the alternatives |
|---|---|---|
| Where state lives | Runner user profile, outside the workspace | Artifact chain expires (≤ 90 days) and races on failed runs; Actions cache evicts after 7 days unused; a git branch would push test data `.gitignore` says must never be pushed; Blob/share needs a long-lived write credential from IT |
| Which runner | Pinned by the `op-pipeline` label | A second Windows runner would otherwise start from an empty state and reuse control codes |
| Concurrency | One `op-pipeline-state` group shared by every pipeline workflow | Two runs would overwrite each other's tracker |
| Missing state | Refuse to run; an explicit `initialize_state` input creates it once | Starting fresh silently is the duplicate-control-code failure |
| Rollback | Dated snapshots + a documented manual copy | A rollback workflow input is not worth building for a rare event |

Accepted trade-off: if AVD-BASCL06-0 is rebuilt or its profile is wiped, the history is
lost (snapshots live on the same disk). The newest tracker artifact (30 days) is the only
copy off the machine.

## Layout on the runner

```
%USERPROFILE%\claims-qa-state\
  op-pipeline\                        current state, restored by every run
    test-data\                        tracker + intake files (all channels/dates)
    .intake-sequence-state.json       filename counter
    store.json                        marker (below)
  op-pipeline-snapshots\
    20261027-143005-123-run42\        tracker + counter as they were BEFORE run 42
    …                                 newest 20 kept
```

`store.json`:

```json
{
  "createdAt": "2026-10-27T14:30:05+08:00",
  "createdByRun": "https://github.com/<owner>/<repo>/actions/runs/123",
  "lastRunNumber": 42,
  "lastRunAt": "2026-10-27T15:02:11+08:00",
  "lastRunUrl": "https://github.com/<owner>/<repo>/actions/runs/456",
  "files": ["test-data/control-code-tracker.xlsx", "scripts/.intake-sequence-state.json"]
}
```

`files` lists the key files that existed at the last save. A restore requires every file
listed, so a file that was saved once and is now gone is detected, while a file that has
never existed yet (the counter before the first S0) is not demanded.

## Components

### `.github/actions/pipeline-state/` — composite action

One shared implementation of restore and save, used by every pipeline workflow.

- `action.yml` — inputs, then one `powershell` step that calls the script.
- `pipeline-state.ps1` — all logic, runnable outside GitHub Actions for the dry run.

Inputs:

| Input | Default | Meaning |
|---|---|---|
| `mode` | (required) | `restore` or `save` |
| `initialize` | `false` | `restore` only: create the store if none exists |
| `state-root` | `''` → `%USERPROFILE%\claims-qa-state` | Lets the dry run use a scratch folder |
| `snapshot-keep` | `20` | Snapshots retained after pruning |

**`restore`:**
1. No `store.json`:
   - `initialize` false → fail: "No pipeline state found at <path>. If this is the first
     run on this runner, re-run with initialize_state ticked."
   - `initialize` true → create `op-pipeline\` and `store.json` (`files: []`), continue.
2. `store.json` exists and any listed file is missing → fail, even with `initialize`:
   "Pipeline state is damaged: <files> missing. Restore from
   op-pipeline-snapshots\ (README § Pipeline state on the runner)."
3. `initialize` true while `store.json` exists → warning, ignored.
4. Snapshot: copy the tracker and counter (those present) to
   `op-pipeline-snapshots\<yyyyMMdd-HHmmss-fff>-run<N>\` (milliseconds, so names
   never collide and sort by age); delete all but the newest
   `snapshot-keep`.
5. Copy `op-pipeline\test-data\` → workspace `test-data\` (robocopy `/E`), and the counter
   → `scripts\`.

**`save`:**
1. Copy workspace `test-data\` → `op-pipeline\test-data\` (robocopy `/E /XF *.lock`; never
   deletes from the store).
2. Copy the counter if present.
3. Rewrite `store.json`: last run number/time/URL, and `files` = the key files present now.

Both modes treat robocopy exit codes 0–7 as success and ≥ 8 as failure.

### Workflow changes

`.github/workflows/op-intake-pipeline.yml` (and every future pipeline workflow):

- `runs-on: [self-hosted, windows, op-pipeline]`
- New input `initialize_state` (boolean, default false).
- `concurrency: op-pipeline-state` (unchanged).
- Inline restore/save steps replaced by the action:
  - restore (`id: restore`) right after `npm ci`, with `initialize: ${{ inputs.initialize_state }}`;
  - save at the end, `if: always() && steps.restore.outcome == 'success'`.
- Tracker artifact retention 7 → 30 days.

### Documentation

README gains § Pipeline state on the runner: what is kept and where, first-run
initialization (including optionally seeding from a local `test-data/` and counter), and
the rollback procedure:

1. Make sure no pipeline workflow is running.
2. On the runner, copy the chosen snapshot's tracker and counter over the ones in
   `op-pipeline\`.
3. Run the workflow with S0–S2 unticked and check "Tracker status (before)".

## Viewing

- Run summary: tracker status before and after (unchanged).
- Artifact `control-code-tracker`: the workbook, 30 days. Control codes and statuses only,
  no member names or member codes. Intake files are never uploaded.

## Testing

Dry run of `pipeline-state.ps1` against a scratch `state-root` (no GitHub, no runner):

| Case | Expected |
|---|---|
| Empty root, restore | Fails "No pipeline state found" |
| Empty root, restore with initialize | Creates `store.json` with `files: []` |
| Save with tracker only, then restore | Restores tracker; no counter demanded |
| Save with tracker + counter, delete the counter, restore | Fails "damaged", names the counter |
| Same, restore with initialize | Still fails |
| 22 restores | 20 snapshot folders remain, newest kept |
| Save with a `.lock` file in test-data | Lock not copied |

On the runner, in order:
1. Tracker-only run (S0–S2 unticked) → fails "No pipeline state found".
2. Optionally seed `op-pipeline\` from a local `test-data\` and counter, then the same run
   with `initialize_state` → succeeds, `store.json` created.
3. Second tracker-only run → same codes in "before"; one snapshot folder.
4. S0 only, then S1 → tracker before/after match expectations.

## Out of scope

- Workflows for S3–S10 (they will reuse this action).
- Sharing the tracker with local runs.
- Off-machine backup beyond the tracker artifact.
- Automatic cleanup of old intake date folders.
